# 개인 커리어 지원

현재 요청 범위와 이미 확인한 지원 건에서 시작한다. 로컬 포크에서 직접 실행할 때는 [공통 가드레일](references/guardrails.md)을 읽고 포크의 `bin/`을 사용한다. Claude Code 프리앰블이 실행됐다면 `JS_BIN`으로 포크의 `bin/` 위치를 확인한다. 작업 자료와 패킷은 비공개 로컬 경로에 보관한다. 봇·클라우드에서 시작했으면 로컬 포크 세션으로 돌아가 작업하도록 안내하고 사용자가 제공한 공개 공고만 검토한다.

지원 건을 이어갈 때는 ID로 패킷 상태를 먼저 조회한다. ID가 모호하면 회사·직무·공고 링크를 물어 범위를 정한다. 이전 답변이 현재 공고·폼에 그대로 적용되는지 확인하고, 사용자가 이미 제공한 자료와 결정은 다시 묻지 않는다. 여러 공고를 고르면 공고별로 지원 사이트, 자료, 패킷, 승인, 접수, 학습 계획을 관리한다. 패킷 조작은 [패킷과 접수](references/packet.md)를 따른다.

## 1. 로컬 기록과 지원 조건 확인

- 사용자가 지정한 Markdown 파일이나 디렉토리를 우선한다. 경로를 주지 않았으면 현재 작업 폴더와 바로 위 폴더에서 커리어·경력·이력서 이름을 가진 Markdown의 **파일명만** 좁게 확인한다. 포크 안의 테스트·샘플·문서와 숨김 디렉토리는 제외한다. 여러 후보, 소유권이 불명확한 파일, 접근 제한이 있는 경로는 후보를 열기 전에 사용자에게 경로 하나를 확인한다. 자료가 없으면 경로 또는 관련 발췌를 요청한다.
- 선택한 기록에서 지원 판단에 쓰일 역할, 경력 기간, 프로젝트, 직접 기여, 측정 조건을 읽는다. 근거는 로컬 파일명과 절 또는 줄 범위로 남긴다. 최신 사용자 진술에서 선호를 확인하고, 날짜나 기여에 충돌이 있으면 필요한 사실만 확인한다. 원본 갱신은 사용자가 요청한 범위에서 한다.
- 직무·경력 레벨, 희망 지역·출근/원격·출장, 고용 형태, 연봉 등 이번 탐색에 영향을 주는 조건을 확인한다. 필수·선호·미정은 사용자의 표현을 따른다. 결정에 영향을 줄 미정 조건만 질문한다. 검색어에는 직무와 공개 조건만 넣는다.

## 2. 선택할 공고와 사이트 제시

- `job-search`의 수집·본문 확인·매칭 방법을 재사용한다. 방향이 불명확하면 `strategy`, 회사를 비교해야 하면 `company-research`를 활용한다. 사용자가 공고와 지원 경로를 이미 골랐다면 그 선택을 확인해 3단계로 간다.
- 채용사·공식 ATS의 원문과 실제 지원 링크를 우선 확인하고, 공고판이 별도 지원 경로를 제공하면 함께 표시한다. 같은 공고를 묶되 수시/공채, 직무, 경력 구분, 공고 ID가 다르면 독립 건으로 둔다. 확인일(KST), 접수 상태·마감, 업무와 필수·우대 요건, 근무 조건을 기록한다. 조건이나 마감이 불명확하면 확인이 필요한 사항으로 남긴다. 검색 결과 요약만 확보한 공고에는 점수를 매기지 않는다.
- 접수 중인 공고를 필수 조건 충족 여부와 실제 업무에 연결되는 경력 근거, 사용자가 밝힌 선호 순으로 비교한다. 순위마다 맞는 근거, 미충족·미확인 조건, 선택이 바뀔 이유, 채용사 원문 및 공고판 링크를 보여준다. 지원할 공고를 고르고, 공고마다 실제 지원 사이트를 하나 정하도록 요청한다. 추천이나 순위는 사용자의 선택을 대신하지 않는다.
- 선택한 공고마다 공고 ID, 원문 URL, 확인 시각(KST)과 함께 확인한 채용 본문·업무·요건·전형·마감 정보를 비공개 로컬 Markdown으로 보관한다. 페이지가 닫힌 뒤에도 어느 시점의 요건을 근거로 준비하는지 추적할 수 있게 한다. 별도 작업 폴더를 지정받지 않았다면 상태 루트의 `personal-career/<지원 ID>/posting.md`에 보관하고 경로를 알려준다. 패킷 입력 디렉토리는 별도로 둔다.

## 3. 실제 폼을 확인하고 문항별로 작성

- 선택한 사이트에서 회사, 직무, 공고 ID가 일치하는 폼을 확인한다. 각 단계에서 실제 질문·선택지·필수 여부·최소/최대 분량·계산 단위(공백, 줄바꿈, 바이트 등)·첨부 형식/용량/개수·동의 항목을 원문 및 확인일과 기록한다. 프로필/이력서 선택, 화면에서 자동 입력된 값과 공개 범위도 확인한다. 로그인·인증·CAPTCHA는 사용자가 처리한다. 읽기 도구가 없거나 로그인 뒤 문항이 열리지 않으면 필요한 빈 폼 캡처나 항목 원문을 요청한다. 일부 문항만 확인했으면 미확인 항목을 남긴다.
- `resume`, `career-history`, `cover-letter`, `portfolio`에서 요구된 산출물만 만든다. 각 문항을 실제 요구와 사용자 근거에 연결한다. 문항 원문, 출처(폼 URL·화면·확인일), 답변, 제한과 입력 수치, 사용한 근거(로컬 기록 위치·공개 링크)를 검토표로 묶는다. 사이트 카운터와 검증을 우선하며, 바이트 인코딩이나 공백 규칙이 불명확하면 추측한 계산을 최종 검증으로 쓰지 않는다.
- 개인 역할과 팀 성과를 원자료대로 표현하고 내부 고객명·기밀·제3자 연락처의 공개 범위를 확인한다. `review`의 서류 일관성 점검을 적용한다. 필수 미확인 항목, 임시 표시, 분량 초과, 모호한 동의가 있으면 해당 항목을 해결한 후 최종 검토를 진행한다. 실제 폼에 넣는 문장과 근거 검토표는 별도로 보관한다.

## 4. 포트폴리오가 필요한 경우 제작

포트폴리오가 필수면 허용 형식에 맞춰 준비한다. 선택 항목이면 사용자에게 생략, 기존 자료 제출, 공고에 맞춘 새 자료 제작 중 가능한 선택지와 각 근거를 제시한다. 슬라이드로 제작하는 경우 사용자가 Cowork에 맡기기로 하면 [Cowork 제작과 검증](references/cowork-pptx.md)을 따른다. PDF만 받는 곳도 PPTX로 제작한 후 PDF를 내보낼 수 있다. 링크만 받는 곳은 제출할 링크의 대상과 열람 권한을 확인한다. 검증을 마친 제출용 파일 또는 링크를 검토본에 포함한다.

## 5. 패킷을 검토하고 접수 확인

`jobstack-packet`으로 실제 지원 폼의 확정 입력·첨부를 스냅샷으로 저장한다. 스냅샷 리비전과 함께 회사·공고판·지원 사이트·공고 URL·첨부 원본·폼에 들어갈 모든 값·동의 선택을 보여준다. 사용자가 해당 리비전을 명시적으로 승인하고 제출 주체를 선택해야 한다. **기본은 사용자의 브라우저 수동 제출**이다. 에이전트 제출은 이 공고와 리비전에 대해 사용자가 **한 번 클릭하도록 명시적으로 허용**했을 때만 가능하다. 내용을 승인한 표현, 이전 공고에서의 승인, 일괄 지원 요청으로 최종 버튼을 누르지 않는다.

제출 직전 접수 가능 여부와 실제 폼을 동결본과 대조하고, [패킷과 접수](references/packet.md)대로 한 번의 시도를 처리한다. 대조 중 값·첨부·동의·목적지가 바뀌면 재검토와 새 승인이 필요하다. 접수 화면·지원 내역·접수 메일 등 일치하는 성공 증거가 있어야 접수 완료로 기록한다. 모호한 결과에서는 시도를 보류 상태로 두고 접수 여부를 확인한다. 공식적으로 제출되지 않았음이 확인되면 실패를 기록하고, 다시 진행할 때 새 승인과 1회 제출 허용 범위를 확인한다.

## 6. 접수된 공고 기준으로 준비

`status`의 접수된 스냅샷과 접수 증거, 로컬에 보관한 날짜가 있는 공고의 업무·요건, 확인된 전형 정보를 기준으로 한다. 요청된 경우 `tracker`에서 같은 공고의 기존 행을 찾아 갱신한다. 공고별 학습 계획에는 요구 역량과 제출 답변별 후속 질문, 확인할 사실 또는 보완할 기술, 실습·모의 질문, 완료 기준을 넣는다. 가능한 공부 시간과 확인된 전형 일정을 배정에 반영한다. 전형 미확인 사항은 표시한다. `mock-interview`의 해당 모드를 재사용해 제출한 문장에 근거한 연습으로 연결한다.
